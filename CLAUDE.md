# Sufra — Agent Orientation

Read `PRD.md` before any non-trivial change. It is the source of truth for product decisions, milestones, positioning, and architecture intent. This file is the short orientation; PRD.md is the long-form.

## What this is

A photo-first calorie tracker for households. **Host-deployed** on the host's own Cloudflare account, **host-paid inference**, multi-user (host provisions accounts for end users). PWA, English + Arabic, Middle Eastern cuisine as a first-class citizen.

Two user roles: **host** (technically capable, manages the deployment, also eats) and **user** (the people whose food gets photographed — never sees the deployment or config).

## Stack

- **Frontend:** Vite + React 19 + TanStack Router (file-based) + TanStack Query + Tailwind v4 + shadcn
- **Backend:** Hono on Cloudflare Workers, single Worker serving SPA assets and `/api/*`
- **Database:** Cloudflare D1 via Drizzle ORM
- **Storage:** Cloudflare R2 (binding `BUCKET`)
- **Auth:** better-auth with `username` + `admin` plugins; no email anywhere
- **PWA:** vite-plugin-pwa with workbox (autoUpdate; `/api/*` is NetworkOnly)
- **Inference:** OpenRouter (key as Cloudflare secret, not in DB or admin UI)
- **Dev:** `@cloudflare/vite-plugin` runs Worker inside `vite dev` against workerd

## Run it

```
pnpm dev                    # vite + workerd, one port
pnpm typecheck              # tsc -b across app + worker + node projects
pnpm build                  # tsc -b && vite build (produces dist/client + dist/sufra)
pnpm lint
pnpm db:generate            # drizzle-kit generate (after schema changes)
pnpm db:migrate:local       # wrangler d1 migrations apply DB --local
pnpm db:migrate:remote      # wrangler d1 migrations apply DB --remote
pnpm cf-typegen             # regen worker-configuration.d.ts after wrangler.jsonc edits
pnpm deploy                 # build + wrangler deploy
```

## Auth model

- **One auth instance per request** — `createAuth(c.env)` inside the route handler. Don't try to memoize it at module scope (env isn't available there).
- **No email anywhere.** better-auth requires the `email` column on `user`, so we store `<username>@sufra.local` (non-routable). Users sign in by username only.
- **No public signup.** `disabledPaths: ["/sign-up/email"]` blocks the HTTP route. Internal `auth.api.signUpEmail()` still works — used by the setup wizard. End users are created via the admin plugin's `auth.api.createUser()`.
- **Roles:** `host` (admin-equivalent) and `user`. Defined via better-auth's access controller in `worker/auth/permissions.ts`; admin plugin enforces them.
- **First deploy:** `POST /api/setup` only works while zero hosts exist. Creates the host, signs them in, inits `app_settings` singleton.
- **Route guards:** `__root.tsx` `beforeLoad` does one fetch (setup status + session in parallel), returns `{ needsSetup, session }` as context. Leaf routes do sync conditional redirects from that context. No separate auth-guard helpers.

## Conventions

- **Comments:** default to none. Only write a comment when the *why* is non-obvious (hidden constraint, surprising workaround). Never restate what the code does. Never reference PRD sections, milestones, or "current fix" in comments — that belongs in commit messages / PR descriptions.
- **Type safety:** use the Hono RPC client (`api.api.*.$get()`/`$post()`) for our own routes, not raw `fetch`. Use the `authClient` for `/api/auth/*` routes.
- **Validation:** zod v4 + `standardSchemaResolver` (from `@hookform/resolvers/standard-schema`). The older `zodResolver` is pinned to zod 3 internals and breaks.
- **No `archive` table for users.** Cascade deletes on `user_profile` and `weight_log`. Soft-disable is via the admin plugin's `banned` flag.

## Deviations from PRD worth knowing about

These have been incorporated into PRD.md but are easy to miss:

- **OpenRouter API key** is **not** in the admin UI. It's a Cloudflare secret (`wrangler secret put OPENROUTER_API_KEY`). Model *selection* is in `app_settings`.
- **No forced password change** on first login. End user signs in with whatever password the host set; they can change it from Profile later.
- **Auth** is better-auth, not the "rolled, argon2id" plan in §8.1 — uses scrypt via Web Crypto (no WASM).
- **No top-level macros in `MealAnalysis`.** Totals are `sum(foods[i].field)`, computed at read time. Eliminates the denormalization-drift class of bug. The DB will denormalize `kcal_total` per meal for fast day-view queries.
- **AI estimate is immutable; user override is separate.** Each meal record stores `ai_analysis` (the full MealAnalysis result, never mutated) and `override: { kcal?, proteinG?, carbsG?, fatG? }` (mutable, per-field). Display = `override.field ?? sum(foods.field)`. The original AI line stays visible as muted reference text. Users cannot edit the AI numbers directly.
- **`keyNutrients` deferred to v2.** Fiber / sugar / sat fat / sodium dropped from the v1 schema; calorie + macros are the v1 focus.
- **Saved meals: explicit match only.** The AI never sees saved meals. Any logged meal can be marked saved; user picks from a saved-meals list to re-log (copies `ai_analysis` + `override` into a new entry). The "implicit match via prompt injection" half of PRD §6.5 was dropped — non-deterministic, prompt-cost-forever.
- **No two-pass clarification round-trip in v1.** `priorAnalysis` / `clarificationAnswers` removed from the provider input. The model still produces clarification questions for advisory display. The actual round-trip will be designed end-to-end when M4 lands the clarification UI.
- **One English system prompt for all locales.** `getSystemPrompt(locale)` appends a short locale instruction telling the model to output user-read fields (`dishName`, `foods[].name`, `clarifications[].question`, `clarifications[].options[]`, `notAnalyzableReason`) in the target language. Adding a new language = one line in `LOCALE_NAMES`. No per-language prompt translations.

## Critical wrangler.jsonc bits

- `not_found_handling: "single-page-application"` — assets layer serves `index.html` for unknown paths (SPA routing).
- `run_worker_first: ["/api/*"]` — **required for production**. Without this, the assets layer would intercept API routes via SPA fallback. Dev works without it because the Vite plugin always routes through the Worker.
- `migrations_dir: "./worker/db/migrations"` on the DB binding.

## Gotchas hit during setup

- D1 + Drizzle "boolean" mode emits `DEFAULT true/false` in SQL; SQLite accepts it. Don't try to "fix" the migration file.
- ESLint may flag stale "unused import" diagnostics between two sequential Edit calls in the same file. Re-run `pnpm lint` to confirm; the file itself is usually fine.
- `worker-configuration.d.ts` is committed (it's huge but stable). Regenerate via `pnpm cf-typegen` whenever `wrangler.jsonc` bindings change.
- `pnpm` overrides force `sharp@^0.34.5` to avoid the duplicate libvips dylib warning from `@vite-pwa/assets-generator`.
- The shadcn `form` component silently no-ops in v4.7; use react-hook-form + bare Input/Label.
