# Identity/person split; no-email username+password auth on Kysely + KV

Better Auth's credential table is renamed `identities` and split from an app-owned `users` person table that **shares the same primary key** — one id per human, the universal ownership anchor every resource references as `userId`. Auth stays **no-email username + password**, Grafana-style: Setup creates the first Host; the Host provisions Members by username; no email lives anywhere. Better Auth runs on the **Kysely-D1 dialect** (the Drizzle adapter is dropped); sessions live in **Cloudflare KV** via `secondaryStorage` with a `Math.max(ttl, 60)` clamp; the instance is built **once per isolate** (cached at module scope), reversing the old per-request `createAuth`. The `username` + `admin` plugins stay. A `user.create.after` hook **provisions** the `users` row with an idempotent `INSERT OR IGNORE` on the shared id. `CurrentUser = { id, username, role }`; `role` / `banned` / `username` live on `identities` (credential), and the `users` row is the thin Member-as-person aggregate root (`id`, `createdAt`, `updatedAt`).

## Why

There is a bright line between the **credential** — Better Auth's lifecycle, regenerated by the framework, never something the app may drift — and the **person**, which the app owns. The shared primary key is the anchor: every domain row references the human by the same id whether you reach it through the credential or the person. Putting both behind one id means no foreign-key indirection and no synchronization between two surrogate keys.

Kysely decouples Better Auth from the app's now-non-Drizzle persistence (ADR 0009) — the auth subsystem and the domain no longer share a query builder. KV for sessions avoids the D1 read-after-write login flicker (write a session row, immediately read it on the same request, get nothing). Build-once is correct because isolate bindings are stable for the life of the isolate — there is no per-request env to thread, so the CLAUDE.md "don't memoize auth at module scope" rule is reversed here.

The Grafana model — first user is the admin, the admin provisions the rest, no public signup, no email — fits a host-deployed household app that ships with no email infrastructure. The `users` root earns its place as the **aggregate root** for the Member because its `profile_snapshots` and `weights` are owned collections (ADR 0011), not because it holds profile columns: Sufra's profile is an append-only log, so "onboarded" is **derived** from "has ≥1 `profile_snapshot`," never a column on `users`.

## Considered alternatives

- **One Better Auth `user` table carrying all profile fields.** Rejected — the credential/person split is the point, and the profile is append-only logs (ADR 0011) that don't belong on the credential row anyway.
- **Passwordless `emailOTP` (the house style's default).** Rejected — contradicts the no-email premise; there is no channel to deliver a code.
- **Sessions in D1.** Rejected — read-after-write flicker on the login round-trip; KV is the correct session store.
- **Per-request `createAuth(env)` (the old pattern).** Rejected — build-once is correct; isolate bindings are stable, so there is nothing to rebind per request.
- **`role` on the `users` person row.** Rejected — role is an authorization fact (ADR 0013), which is a credential concern; it stays on `identities`.
- **A separate surrogate primary key on `users`.** Rejected — the shared PK is what guarantees no drift between credential and person; a second key reintroduces the synchronization problem the split exists to remove.

## Mechanism

- `auth/` holds the Better Auth subsystem: one cached instance on the Kysely-D1 dialect, KV `secondaryStorage` for sessions, the `username` + `admin` plugins.
- `auth.cli.ts` is generation-only — it mirrors the `username` + `admin` plugin config so the Better Auth CLI emits `0001_better_auth.sql` (the credential schema baseline; see ADR 0009's reset baseline).
- The `user.create.after` hook runs `INSERT OR IGNORE` into `users` on the shared id. It is idempotent, so re-firing on `admin.createUser` provisions exactly one person row and never errors. **Verify the hook fires on `admin.createUser`** — the admin plugin's create path is the Member-provisioning entry point.
- The app reads `username` from `identities` (read-only) by the shared id when a view needs it. It **never mirrors** `username` onto `users` — there is one source for the credential fields.
- The `CurrentUser` bridge (`{ id, username, role }`) is assembled from the session + the credential row and handed to the Effect handler; ownership scoping and the role gate both read it (ADR 0013).

## Consequences

- Add `kysely` + `kysely-d1` dependencies (with the `kysely@0.28.17` pin) and a KV namespace binding to `wrangler.jsonc`.
- The Drizzle auth adapter is removed; the credential schema comes from `auth.cli.ts` → `0001_better_auth.sql`.
- Reverses CLAUDE.md's "don't memoize auth at module scope" — the instance is now module-scope cached, one per isolate.
- The Member-as-person aggregate (ADR 0011) is rooted on the `users` row; its owned collections, not profile columns, justify the root.
- The Password link flow (ADR 0016) is the no-email credential handoff — the Host hands a link to a provisioned Member out of band, since there is no email channel.
- This ADR establishes the `identities`/`users` split that the whole `worker/` tree references as `userId`; it lands first in the tracer-bullet slice order (ADR 0009).
